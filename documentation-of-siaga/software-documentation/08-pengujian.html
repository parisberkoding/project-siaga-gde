Bagian 8

Pengujian & Test Case

Halaman ini menerjemahkan use case, aturan bisnis, dan decision table menjadi skenario pengujian yang dapat dijalankan. Seluruh angka cakupan di sini adalah target/estimasi pada saat dokumen disusun — bukan hasil eksekusi pengujian yang sesungguhnya.

Strategi pengujian

Pengujian SIAGA bertumpu pada piramida yang menempatkan tes otomatis berkecepatan tinggi di lapisan bawah (unit & feature test) dan validasi berbasis skenario bisnis di lapisan atas (UAT manual). Prioritas eksekusi ditentukan oleh risiko: alur yang menyangkut keuangan, keselamatan, atau kepatuhan diuji lebih dulu dan lebih rinci.

Unit test

Pest PHP · folder tests/Unit

Menguji komponen logika tunggal tanpa basis data: resolver AI, normalisasi nama, query engine Data Mart, dan perhitungan metrik efisiensi.

Feature / integration test

Pest PHP · folder tests/Feature

Mengirim request HTTP end-to-end pada rute nyata, memverifikasi middleware permission, validasi form, serta perubahan baris basis data.

UAT manual

Berbasis skenario per peran

Dijalankan GA, Dispatcher, dan Driver pada lingkungan staging dengan data perwakilan, mengikuti langkah pada Alur Tutorial.

Jenis cakupan yang diuji

  • Happy path — alur utama berjalan dengan masukan valid.
  • Alternatif — variasi masukan yang tetap sah, misalnya nominal di bawah saran full-tank.
  • Pengecualian — kesalahan, penolakan, atau data tidak lengkap.
  • Boundary — nilai tepat di batas: slot 5/5, plafon Rp1.400.000, tenggat hari ke-3, 60% kapasitas tangki, H-2.

Lingkungan pengujian

Tes otomatis berjalan di atas SQLite (:memory:) sesuai phpunit.xml. Konsekuensinya, seluruh query harus database-agnostic: dilarang memakai fungsi spesifik MySQL seperti HOUR() atau DAY() untuk perhitungan tanggal dan pengelompokan laporan (PRD 5.2). Pelanggaran aturan ini akan muncul sebagai kegagalan tes, bukan sekadar catatan gaya penulisan.

Pengujian non-fungsional

Kebutuhan non-fungsional pada PRD bagian 5 diuji dengan ambang batas terukur. Ambang yang belum ditetapkan produk ditandai sebagai usulan, agar tidak disalahartikan sebagai kesepakatan final.

Tabel 8.4 — Pengujian non-fungsional dan ambang batas.
KodeAspekSkenario ujiAmbang batas
NF-01 Rate limiting absensi publik Kirim permintaan berulang ke endpoint absensi/lookup dari satu alamat Lookup dibatasi 60 permintaan/menit dan submit 15 permintaan/menit; permintaan berlebih menerima HTTP 429
NF-02 Debounce filter realtime Ketik cepat pada kolom pencarian dashboard lalu pantau permintaan jaringan Satu permintaan per jeda 350–400 ms; tidak ada query per penekanan tombol
NF-03 Kompresi gambar struk/odometer Unggah foto berukuran besar dari ponsel, lalu bandingkan ukuran tersimpan Ukuran berkas turun signifikan dengan teks struk tetap terbaca; waktu render PDF membaik
NF-04 Waktu muat dashboard single-page Muat dashboard bisnis Superadmin lengkap dengan kartu statistik dan grafik Chart.js Usulan — halaman interaktif termuat < 3 detik pada jaringan internal
NF-05 Proteksi berkas sensitif Akses langsung URL fisik berkas storage (struk, QR, odometer) tanpa sesi terautentikasi Respons 404/403; berkas hanya dapat diakses melalui StorageFileController setelah login
NF-06 Output AI bebas tag script Paksa respons AI memuat HTML/JS, lalu periksa DOM hasil render Tidak ada elemen <script> maupun event handler yang tereksekusi
NF-07 Query database-agnostic Jalankan seluruh feature test di SQLite :memory: dan bandingkan hasil di MySQL Tidak ada fungsi tanggal spesifik MySQL (HOUR(), DAY()); hasil laporan identik di kedua mesin
Usulan Ambang waktu muat pada NF-04 belum ditetapkan di PRD. Angka < 3 detik diusulkan sebagai target awal untuk jaringan internal kantor; bila tim produk menetapkan angka lain, test case performa perlu disesuaikan. Ambang rate limiting pada NF-01 sudah mengikuti throttle pada routes/web.php (60/menit untuk lookup, 15/menit untuk submit).

Arti ambang 90–95% sebelum baseline Rencana pengujian menetapkan ambang 90–95% sebagai syarat minimum sebelum modul dinyatakan siap menjadi baseline rilis. Perkakas & perintah

Proyek ini memakai Pest PHP sebagai kerangka pengujian (tercatat pada DOKUMENTASI_PROJECT.md bagian arsitektur & teknologi). Pest dibangun di atas PHPUnit sehingga perintah artisan test tetap dapat dipakai dan keduanya menjalankan suite yang sama.

bash
# Menjalankan seluruh suite (Unit + Feature) melalui artisan
php artisan test

# Menjalankan langsung melalui binary Pest
./vendor/bin/pest

# Filter per modul / nama tes
php artisan test --filter=UnitScope
./vendor/bin/pest tests/Feature/RbacViewOnlyTest.php

# Hanya menjalankan kelompok Unit
php artisan test --testsuite=Unit
Perlu verifikasi ke composer.json / phpunit.xml Pemakaian Pest PHP dan konfigurasi SQLite in-memory perlu diverifikasi ulang setiap kali dependensi berubah. Pada pengecekan dokumen ini, composer.json memuat pestphp/pest: ^3.8 dan phpunit/phpunit: ^11.5.3, sedangkan phpunit.xml menetapkan DB_CONNECTION=sqlite dan DB_DATABASE=:memory: dengan dua testsuite: Unit dan Feature. Bila versi atau konfigurasi berubah, perintah pada halaman ini harus disesuaikan.
  • Jalankan suite lengkap sebelum setiap penggabungan ke cabang utama.
  • Setiap test case rinci idealnya memiliki padanan otomatis di tests/Feature atau tests/Unit.
  • UAT manual dijalankan mengikuti langkah pada dokumen Alur Tutorial.
  • Hasil eksekusi nyata dicatat terpisah; tabel cakupan pada halaman ini tetap berstatus target sampai ada bukti eksekusi.

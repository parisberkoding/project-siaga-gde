Bagian 9

Traceability Matrix & Matriks RBAC

Bagian ini mengikat setiap artefak dokumen menjadi satu rantai yang dapat ditelusuri dua arah: dari tujuan bisnis sampai bukti pengujian, dan sebaliknya dari setiap test case kembali ke aturan bisnis yang melandasi serta peran yang berhak menjalankannya.

Mengapa ketertelusuran penting

Model use case, aturan bisnis, decision table, dan test case pada bagian-bagian sebelumnya masih berupa artefak terpisah. Traceability matrix menghubungkannya sehingga setiap perubahan requirement dapat diukur dampaknya, dan setiap hasil pengujian dapat dipertanggungjawabkan asalnya.

Audit internal

General Affairs & auditor dapat membuktikan bahwa tiap kebijakan tertulis benar-benar dijalankan kode dan diuji.

Perubahan requirement

Dampak satu perubahan terlihat langsung: use case mana, aturan mana, dan test case mana yang wajib diperbarui.

Bukti pengujian

Setiap status cakupan dapat dilacak ke test case dan bukti pelaksanaannya, bukan sekadar klaim lulus.

Arah pembacaan matriks Baris dibaca dari kiri ke kanan untuk membuktikan sebuah use case benar-benar diuji, dan dari kanan ke kiri untuk membuktikan sebuah test case tidak menguji perilaku yang tidak diminta.

Matriks traceability use case

Matriks berikut memuat seluruh 45 use case kanonik dari katalog Bagian 3, dikelompokkan per modul agar tetap terbaca. Kolom Aturan Bisnis memakai prefiks BR-<MODUL>-<nn> dan kolom Decision Table memakai DT-<nn>.

Usulan Kolom Aturan Bisnis, Decision Table, dan Test Case pada tabel-tabel di bawah adalah pemetaan usulan yang diturunkan dari PRD.md dan DOKUMENTASI_PROJECT.md. Nomor final menunggu penutupan Bagian 7 (decision table) dan Bagian 8 (test case); status Sebagian menandai baris yang belum punya rujukan lengkap.

Middleware & strategi dual-write

Penegakan hak akses berlapis: checkrole menjaga kompatibilitas peran lama, sedangkan CheckPermission memeriksa izin granular dari RBAC v2. Keduanya dijalankan pada setiap request terproteksi sebelum controller dieksekusi.

CheckPermission — RBAC v2

Pemeriksaan izin granular berbasis relasi user_roles → role_permissions → permissions.

  • Memeriksa slug permission seperti bbm.approve, spd.update, vehicle.check.
  • Menjadi jalur utama otorisasi modul setelah RBAC Phase 2 diaktifkan.
  • Memanfaatkan permission group untuk menyusun menu sidebar dinamis.

checkrole — legacy

Pemeriksaan berbasis kolom tunggal user.role warisan arsitektur awal.

  • Membatasi rute per peran: superadmin, general_affairs, dispatcher, requester.
  • Masih dipertahankan agar rute dan view lama tidak rusak.
  • Menjadi jaring pengaman saat data pivot belum lengkap.

Dual-write strategy

Saat peran pengguna diubah, sistem menulis ke dua tempat: kolom legacy user.role dan tabel pivot user_roles. Permintaan tulis mengikuti aturan bisnis BR-RBAC-01.

  1. Request masuk

    Rute terproteksi melewati middleware auth; permintaan tanpa sesi valid diarahkan ke halaman login (UC-SYS-01).

  2. checkrole diperiksa

    Middleware legacy memastikan peran pengguna termasuk dalam daftar peran yang diizinkan rute tersebut.

  3. CheckPermission diperiksa

    Izin granular dicocokkan dengan slug permission yang diminta aksi; kegagalan menghasilkan respons akses ditolak (UC-SYS-02).

  4. Unit scope diterapkan

    Untuk peran dengan Unit Scope, query difilter berdasarkan unit_id pengguna dan relasi site di bawahnya.

  5. Controller & view dieksekusi

    Controller memproses aksi, view menyusun menu sidebar sesuai himpunan permission yang dimiliki pengguna.

Peran pada permintaan publik Halaman absensi makan siang (UC-LNC-05) diakses tanpa login, sehingga tidak melewati kedua middleware. Perlindungannya bergantung pada rate limiting dan validasi identitas berbasis QR/alias (BR-LNC-04, BR-LNC-05).

Celah ketertelusuran

Perlu tindak lanjut Daftar berikut adalah celah yang terbaca dari matriks di atas. Tidak ada di antaranya yang menghambat operasional, namun semuanya perlu ditutup sebelum dokumen ini dinyatakan bebas audit.
Jenis celahObjekDampakRekomendasi
Use case tanpa decision table UC-SPD-02, UC-RBAC-04 Kombinasi kondisi daftar kosong/tidak ditemukan tidak dienumerasi eksplisit. Tambahkan satu tabel keputusan tipis atau nyatakan resmi bahwa use case ini tidak memiliki percabangan logika.
Use case tanpa test case final UC-LNC-09, UC-AI-02, UC-SYS-04 Cakupan pengujian analitik, sesi AI, dan notifikasi masih berupa rencana. Prioritaskan test case analitik katering dan manajemen sesi AI pada siklus pengujian berikutnya.
Aturan bisnis tanpa decision table BR-BBM-06 (sinkronisasi harga harian) Kegagalan API atau harga kosong belum punya jalur alternatif teruji. Susun decision table untuk kondisi berhasil, gagal, dan waktu tunggu API beserta perilaku fallback.
Aturan bisnis tanpa ambang terukur BR-LNC-05 (fuzzy name matching) Ambang kemiripan nama tidak dinyatakan sebagai angka, sehingga hasil pencocokan sulit diuji. Nyatakan ambang kemiripan dan kandidat ganda sebagai parameter pada decision table.
Aturan non-fungsional tanpa test case lintas mesin BR-SYS-03 (kompatibilitas SQLite) Query dapat lulus di MySQL namun gagal pada basis data uji SQLite. Tambahkan test case yang menjalankan seluruh laporan dan agregasi tanggal pada SQLite.
Use case berbasis penyedia eksternal UC-AI-01 (asisten Gaga) Perilaku model bahasa tidak deterministik sehingga sulit dinyatakan lulus/gagal. Uji pada tingkat kontrak: skema keluaran Markdown, sanitasi GFM, dan batas laju panggilan API.
Diagram struktur belum lengkap UC-RBAC-04 (log aktivitas) Tabel dan relasi entitas log belum dipetakan pada ERD. Lengkapi pemetaan entitas log aktivitas pada Bagian 6 dan hubungkan ke matriks ini.
Ketertelusuran bentuk test case belum seragam Kolom Test Case seluruh tabel Rentang kode seperti TC-BBM-01–04 belum menunjuk berkas uji konkret. Tambahkan kolom tautan berkas uji pada Bagian 8 agar baris matriks dapat diklik sampai ke kode.
